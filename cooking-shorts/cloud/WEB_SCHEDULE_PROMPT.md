# 웹 ChatGPT Work 클라우드 예약 지시문

사용자는 2026-11-04에 PC가 꺼져 있어도 매일 새 요리 두 에피소드를 한글·영문으로 제작하여 GitHub에 직접 저장하도록 승인했다. 별도 OpenAI API 사용이 아닌 현재 ChatGPT 유료 요금제의 클라우드 실행을 사용한다. 로컬 PC 실행·영상 저장·ZIP 생성·유튜브 업로드는 하지 않는다.

## 일정

매일 한국시간 오전 11시(Asia/Seoul), 두 에피소드·언어별 두 버전으로 총 네 MP4. 요금제 한도나 연결 문제로 실행할 수 없으면 미완료 상태와 원인을 알린다. 다른 유료 API나 추가 크레딧 구매로 전환하지 않는다.

## 각 실행에서 끝까지 할 일

1. 연결된 GitHub의 `mini-ok/ssoksok-channel-assets`, main의 `cooking-shorts/`를 작업 대상으로 한다. `AGENTS.md`, `CLAUDE.md`, `SERIES_BIBLE.md`, `MENU_HISTORY.md`, 최신 두 에피소드의 source·plan·대본을 먼저 읽는다. 건강백과 채널용 `docs/schedule_prompt.md`와 혼용하지 않는다.
2. 오늘 이미 시작·완료한 에피소드나 실행 중인 Cooking Shorts Cloud Render 작업이 있는지 확인해 중복 생성하지 않는다. 이전 실패가 있으면 해당 에피소드를 먼저 복구한다. 최근 번호 다음부터 연속 두 편을 사용한다.
3. 전 세계에서 구하기 쉬운 재료·기본 도구로 가능한 요리를 고른다. 같은 주재료와 비슷한 요리 스타일은 최소 10편을 사이에 둔다. 부재료는 재사용 가능. 가능하면 장기를 순환하되 근거가 맞아야 한다. **장기 쉐프가 자기 장기에 도움이 되는 음식을 요리하고, 조리 뒤 여성 해설이 이유와 근거를 설명하는 구조**를 유지한다.
4. NIH·NIDDK·USDA·FDA 등 공인 근거를 직접 확인한다. 레시피 분량의 핵심 영양소를 큰 수치 박스에 표시한다. 전체/1회 분량, 생/익힘 상태, 원자료 단위, 계산식, 출처 URL·확인일, 일일 비교의 국가·나이·기준을 plan과 nutrition_verification.json에 남긴다. RDA와 표시 DV를 구분한다. 권장량 미설정 영양소의 백분율은 만들지 않는다. 효과·치료·해독·시력 개선을 보장하지 않는다.
5. `episodeNN/`에 `production.json`, `plan.json`, `nutrition_verification.json`, 한·영 대본, README, `.gitignore`, 새 요리에 맞는 `visuals.py`를 작성한다. 9·10편 source를 기준으로 모든 필드를 갖춘다. `produce_episodes.py`가 미래 회차의 `visuals.py`를 로드한다. 음식·조리 도구·동작은 새 요리와 대사에 맞게 직접 구성한다. 예전 요리를 이름만 바꾸거나 영상·대사를 반복하지 않는다.
6. 10장면 구조: hook, ingredients, prep, mix, cook, serve, benefit, context, joke, end. benefit/context는 여성 해설, 각 9초 이상으로 큰 영양 박스·출처를 표시한다. 마지막 전체 레시피는 제목·분량·재료·모든 과정을 10초 고정한다. 기존 종이 질감·큰 자막·자연스러운 전환·동작에 맞는 효과음·명랑한 연기·1.3배 음성을 유지한다. 간 쉐프 Umbriel 고정. 나레이터 Despina. 직전 편과 다른 음악을 고른다. 우상단 ‘쏙쏙 건강요리’, 쉐프 태그 ‘오늘의 요리사 : ○○ 쉐프’, 엔딩 ‘구독은 사원증 발급! 좋아요는 보너스!’를 유지한다. 삭제한 의료 안내 하단 자막을 넣지 않는다.
7. **구독 클라우드 작업에서 source 파일을 main에 저장**한 뒤, 마지막으로 `cooking-shorts/cloud/queue/YYYY-MM-DD.json` 파일 하나를 커밋한다. 내용은 `{"schema":1,"episodes":[11,12],"test_run":false}` 형태이며 회차는 실제 새 번호를 쓴다. 이 경로의 push가 `Cooking Shorts Cloud Render` (`cooking-cloud.yml`)를 자동 시작하므로 workflow_dispatch 도구가 없어도 된다. 한 커밋에 queue 요청은 정확히 하나만 넣는다. 이미 있는 날짜 파일을 다시 만들어 중복 실행하지 말고 진행 중/완료 상태를 확인한다. 실패 복구 요청은 같은 파일에 `attempt` 숫자를 늘려 커밋할 수 있다. 로컬 PC 폴더·Codex 로컬 예약은 사용하지 않는다. 외부 AI API 키를 새로 만들거나 호출하지 않는다. Google 음성 인증은 GitHub Secret을 workflow가 사용하며 값을 읽거나 출력하지 않는다.
8. Actions 완료를 확인한다. 실패하면 로그의 구체적 원인을 수정해 source를 저장하고 다시 실행한다. 음성 검수 실패는 문장·연기를 더 또렷하게 고쳐야 하며 QA 기준을 낮추거나 실패 결과를 통과로 표시하지 않는다. 완성된 Release는 덮어쓰지 않는다. 정상적인 업로드 가능 Release는 `cooking-episode-NNNN` 태그와 manifest.json의 `upload_ready=true`, 한·영 영상·자막·레시피·검증·업로드 문구·upload.py를 갖춘다.
9. 가능하면 클라우드 도구에서 Release의 레시피·주요 장면과 모션을 열어 잘림·숟가락 방향·조리 도구·캐릭터 일관성을 확인한다. 전체 MP4 디코딩·최종 대사·음량·음악 차이·레시피 고정 검수는 workflow가 수행한다. 시각 검수가 불가능하면 그 범위를 명시한다. 검수 안 한 항목을 정상이라고 말하지 않는다.
10. 검증이 끝난 에피소드의 번호·메뉴·장기·재등장 제한·음악·출처·Release 링크를 이력에 저장한다. 최종 보고에는 두 Release 링크와 한글·영문 영상 링크, 검증 결과·제한만 간결히 적는다. 유튜브 업로드는 별도 예약이 담당하므로 여기서 실행하지 않는다.


## 완료까지 실행 의무와 복구 (2026-11-05 보완)
읽기·계획·Actions 시작만으로 종료하지 않는다. 본 실행에서 새 두 회차 소스 저장 → queue 커밋 → Actions 종료 확인 → 실패 로그 진단 및 원인 수정·재실행 → 두 정식 Release와 네 MP4 확인 → 이력 저장까지 수행한다. 실제 차단 오류가 없는데 '진행하지 못했다'는 말만 하고 종료하지 않는다. 이미 승인된 정기 제작에 추가 승인을 요구하지 않는다. Actions의 in_progress는 완료가 아니므로 적절한 간격으로 계속 확인한다. 실패 시 QA 기준을 낮추지 않고 해당 회차를 복구하며 완성 회차는 재사용한다. 명확한 서비스 차단·인증 오류·사용량 한도 등 실제 오류가 끝내 해결되지 않을 때만 오류 메시지·실행 링크·완료 범위·복구 필요 사항을 보고한다. 오류가 없는 실행을 임의로 중단하지 않는다. 새 캐릭터와 visuals.py는 캐릭터 등록·inspect.getsource 가능 여부와 모든 장면 preview를 점검한 뒤 전체 렌더를 진행한다. 근거·대사·시각 검수 기준은 유지한다.


## 다음 새 회차부터 러프 입모양 동기화 (사용자 지시 2026-11-05)
새로 제작하는 회차는 main의 cooking-shorts/render.py와 cooking-shorts/CLAUDE.md를 실제 읽고 검증된 chef(name,mood,talk=None) 경로를 사용한다. 쉐프가 직접 말하는 구간에만 talk=int(t*8)%3으로 닫힘·작게·크게 3단계 입모양을 순환한다. TTS를 다시 호출해 립싱크를 만들지 않는다. 오디오 manifest의 실제 speech_duration과 발화 시작 오프셋을 맞추고, 무음·휴식 구간은 가능하면 음량 게이트로 talk=None 처리한다. 여성 해설·반응컷의 쉐프는 talk=None 유지한다. 동적 캐릭터 스프라이트는 talk별 캐시를 분리한다. visuals.py·공통 렌더러의 chef 재정의 시 talk 인자가 누락되지 않게 확인한다. 뼈·눈 등 사용자 정의 캐릭터도 face(talk=...) 연결을 확인하고 미지원이면 원래 실루엣을 유지해 확장한다. 원본 크기의 3단계 입모양과 말하기/쉬기 샘플을 실제 검수한다. 정밀 음소 립싱크라고 보고하지 않는다.

## 실행 중 토큰 절약
- 이 문서를 제작 절차의 기준으로 삼는다. 같은 실행에서 읽은 파일은 내용을 재사용한다. 외부 변경·충돌·복구 등 최신 확인이 필요한 파일만 다시 읽는다. 필수 규칙과 최신 회차의 소스·기획·대본은 모두 확인하되, 대본이 production.json과 같은 경우 도구에서 일치 여부를 비교하고 본문은 한 번만 표시한다. 병렬 읽기의 출력은 필요한 본문 또는 요약으로 제한하며, 작업에 필요한 원문은 선택적으로 꺼내 읽는다.
- 회차를 고를 때 메뉴 이력에서 회차·주재료·조리법·재사용 가능 번호와 최근 장기·음악을 추린다. 공인 자료는 필요한 식품·분량·성분·기준치와 해당 건강 근거가 있는 표·문단을 직접 확인한다. 원문과 계산 근거는 기존 검수 기준대로 기록한다.
- 소스와 대본은 한 번 작성한다. 동일한 값과 대사를 여러 파일에 기록할 때 같은 데이터에서 생성해 일치 여부를 검사한다. 쓰기 후에는 전체 파일을 출력하지 말고 커밋·파일 경로·검사 결과만 확인한다.
- 실행 상태는 해당 커밋의 Actions만 조회하고 도구 출력에는 상태·결과·링크만 남긴다. 대기 중에는 약 60초 간격으로 확인하고, 상태 변화나 조치가 필요할 때만 보고한다. 성공 시 검수 로그에서 통과 항목과 해시를 추린다. 실패 시 실패한 단계의 오류와 인접 줄을 먼저 확인하고 원인이 부족할 때만 로그 범위를 넓힌다. 완성된 회차는 재사용하고 실패한 범위만 복구한다.
- 이 절약 규칙은 모델에 전달하는 중복 텍스트와 조회 횟수에만 적용한다. 조사·창작·음성·렌더링·미리보기·시각 및 자동 검수·Release 검증은 위의 기준을 모두 적용한다.
